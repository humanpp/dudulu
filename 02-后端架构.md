## 一、架构总览

系统采用**分层解耦**设计。核心原则：

- **情感引擎是纯函数**：不依赖 LLM、数据库、HTTP，可独立测试
- **LLM 客户端是统一接口**：API 模式和本地模式各自实现同一接口，模型无关
- **角色是一等公民**：贯穿存储、引擎、记忆、Prompt 装配
- **用户完全隔离**：每个用户与每个角色的状态和记忆独立
- **主动行为独立于主管道**：作为后台心跳运行，通过 WebSocket 推送给前端
- **流式输出用 SSE**：AI 回复逐 token 推送，比 WebSocket 更简单

### 3.3 预览随机引擎（`core/character/generator.py`）— 不持久化

**关键设计**：前端角色创建向导需要"随机预览"能力，这些操作**不持久化**，只返回预览结果。用户确认后才调用 `create_*` 方法。

```python
class PreviewGenerator:
    """
    职责：为角色创建向导提供不持久化的随机预览。
    与 CharacterGenerator 的区别：不写入数据库。
    """

    def __init__(self, generator: CharacterGenerator):
        self.generator = generator

    def randomize_field(self, template_id: str, field: str,
                        current_profile: dict) -> dict:
        """
        随机单个字段，返回新值。
        用于前端的 🎲 单字段随机按钮。
        """
        template = self.generator.template_loader.load(template_id)
        value = self.generator.randomize_single_field(
            template, field, current_profile
        )
        return {"field": field, "value": value}

    def randomize_all(self, template_id: str,
                      locked_fields: list,
                      current_profile: dict) -> dict:
        """
        随机全部未锁定字段，返回完整档案。
        用于前端的 "随机全部" 按钮。
        """
        template = self.generator.template_loader.load(template_id)
        profile = self.generator.generate(
            template=template,
            locked_fields=locked_fields,
        )
        return {"profile": profile.to_dict()}

    def validate(self, profile_data: dict) -> dict:
        """
        校验当前档案的一致性，返回问题列表。
        用于前端实时校验。
        """
        issues = validate_consistency(CharacterProfile.from_dict(profile_data))
        return {"valid": len(issues) == 0, "issues": issues}
```

    """
    职责：加载模板，支持继承和覆盖。
    """

    def __init__(self, template_dir: str):
        self.template_dir = template_dir
        self._cache = {}

    def load(self, template_id: str) -> Template:
        """加载模板，解析继承链"""
        if template_id in self._cache:
            return self._cache[template_id]

### 3.6 记忆管理器（`memory/memory_manager.py`）

```python
class MemoryManager:
    """
    职责：管理 YantrikDB 中的所有记忆，按 (character_id, user_id) 双键隔离。
    """

    def __init__(self, db_path: str):
        self.db = YantrikDB(db_path)
        self._init_indexes()

    def store_conversation(self, turn: ConversationTurn):
        """存储一轮对话，附带双键和情感标记"""
        memory = {
            "id": generate_id(),
            "character_id": turn.character_id,
            "user_id": turn.user_id,
            "content": turn.text,
            "role": turn.role,
            "is_proactive": turn.is_proactive,
            "timestamp": turn.timestamp,
            "emotion_tag": turn.emotion_tag,
            "intensity": turn.intensity,
            "expression_state": turn.expression_state,
            "importance": self._calc_importance(turn),
            "valence": turn.valence,
            "half_life": self._calc_half_life(turn),
            "tombstone": False,
        }
        self.db.insert(memory)

    def retrieve(self, query: str, character_id: str, user_id: str,
                 current_state: dict,
                 emotion_tag: str = None,
                 time_range: str = None,
                 top_k: int = 5) -> list:
        """
        混合检索（强制双键过滤）：
        - 语义相似度（向量索引）
        - 情感匹配度
        - 时间近因性
        - 关系重要性
        - 衰减门控

        v1.0 新增参数：
        - emotion_tag: 按情感标签过滤
        - time_range: 时间范围过滤（如 "last_7_days"）
        """
        filters = {
            "character_id": character_id,
            "user_id": user_id,
            "tombstone": False,
        }
        if emotion_tag:
            filters["emotion_tag"] = emotion_tag
        if time_range:
            filters["timestamp"] = self._parse_time_range(time_range)

        results = self.db.search(
            query_vector=embed(query),
            filters=filters,
            rerank_fn=lambda m: (
                0.4 * m.semantic_score
                + 0.3 * self._emotion_match(m, current_state)
                + 0.2 * self._recency(m)
                + 0.1 * m.importance
            ),
            top_k=top_k,
        )
        return results
```

def create_llm_client(config: dict) -> LLMClient:

### 3.8 编排管道（`orchestrator/pipeline.py`）

```python
class Pipeline:
    """
    一次完整对话的处理管道。
    """

    def __init__(self, character_manager, memory_manager, classifier,
                 prompt_assembler, llm_client, sedimenter, proactive_state):
        # proactive_state：proactive_state 表的读写入口，供 busy_signal 落库（见第 5.5 步）
        ...

    async def process(self, user_message: str, character_id: str,
                      user_id: str, session_id: str) -> PipelineResult:
        # 1. 加载角色档案
        profile = self.character_manager.get(character_id)

        # 2. 加载该用户对该角色的当前状态
        user_state = self._load_user_state(character_id, user_id)

        # 3. 初始化情感引擎（应用角色覆盖参数）
        engine = EmotionEngine(
            config_path="config/dudulu_config.yaml",
            character_profile=profile,
            user_state=user_state,
        )

        # 4. 应用时间衰减
        engine.apply_decay(hours_elapsed=self._hours_since_last(character_id, user_id))

        # 5. 事件分类（结果除 label/intensity 外还含布尔 busy_signal，见文档 1 第 12.2 节）
        event = await self.classifier.classify(
            user_message, engine.get_full_state(), character_profile=profile
        )

        # 5.5 busy_signal 落库：能走到这一步说明用户刚发了消息，先清空 busy_until
        #     （即文档 1 第 12.2 节的"重新激活"）；命中 busy_signal 则重写 now + 24h，
        #     供心跳第 5 道拦截读取（见 3.11）
        self.proactive_state.clear_busy_until(character_id, user_id)
        if event.busy_signal:
            self.proactive_state.set_busy_until(character_id, user_id, hours=24)

        # 6. 情感引擎更新
        delta = engine.apply_event(event)

        # 7. 记忆检索（按双键过滤）
        new_state = engine.get_full_state()
        memories = self.memory_manager.retrieve(
            query=user_message,
            character_id=character_id,
            user_id=user_id,
            current_state=new_state,
            top_k=5,
        )

        # 8. Prompt 装配
        prompt = self.prompt_assembler.build(
            character=profile,
            expression_state=new_state["expression"],
            affective_state=new_state["affective"],
            memories=memories,
            recent_turns=self._get_recent_turns(character_id, user_id, n=10),
            user_message=user_message,
        )

        # 9. LLM 生成（非流式版本）
        reply = await self.llm_client.generate(prompt)

        # 10. 后处理
        reply = self.post_processor.process(reply)

        # 11. 存储
        self.memory_manager.store_conversation(...)
        self._persist_user_state(character_id, user_id, new_state)

        # 12. 沉淀检查
        self.sedimenter.maybe_sediment(character_id, user_id)

        return PipelineResult(reply=reply, state=new_state, memories=memories)

    async def process_stream(self, user_message: str, character_id: str,
                             user_id: str, session_id: str) -> AsyncIterator:
        """
        流式版本。前 8 步与非流式相同，第 9 步改为流式生成。
        Yields: SSE 事件
        """
        # 1-8 步相同
        ...

        # 9. 流式生成（异常必须转成 error 事件，见 6.6 的事件类型表）
        full_reply = ""
        try:
            async for token in self.llm_client.generate_stream(prompt):
                full_reply += token
                yield {"event": "token", "data": token}
        except Exception as exc:
            # 已吐出去的 token 不回滚：前端保留已显示的文字，并给「重新生成」
            yield {"event": "error", "data": {"message": str(exc), "partial": full_reply}}
            return

        # 10. 后处理
        reply = self.post_processor.process(full_reply)

        # 11. 存储
        ...

        # 12. 沉淀检查
        ...

        # 13. 发送完成事件
        yield {"event": "done", "data": {"state": new_state}}
```

### 3.9 Prompt 装配器（`orchestrator/prompt_assembler.py`）

```python
class PromptAssembler:
    """
    职责：将角色档案、情感状态、记忆上下文组装为完整 Prompt。
    注入方式：文本注入（结构化文本拼接）。
    """

    def build(self, character: CharacterProfile, expression_state: dict,
              affective_state: dict, memories: list, recent_turns: list,
              user_message: str) -> str:

        sections = []

        # 1. 角色档案
        sections.append(self._render_character(character))

        # 2. 说话风格
        sections.append(self._render_speech_style(character.speech_style))

        # 3. 情感状态（文本注入）
        sections.append(self._render_emotion_state(expression_state))

        # 4. 关系状态
        sections.append(self._render_relationship(affective_state))

        # 5. 记忆上下文（按需注入外貌片段）
        if self._needs_appearance(user_message):
            sections.append(self._render_appearance(character.appearance))
        sections.append(self._render_memories(memories))

        # 6. 最近对话
        sections.append(self._render_recent_turns(recent_turns))

        # 7. 用户消息
        sections.append(f"[USER]\n{user_message}\n[/USER]")

        return "\n\n".join(sections)

    def _render_emotion_state(self, state: dict) -> str:
        # 由 PLE/ARO/DOM 映射为 Mood/Energy/Stance 三个定性标签，
        # 统一阈值 ±0.4，映射表见文档 1 第 6.3 节
        def label(value, low, mid, high):
            if value >= 0.4:
                return high
            if value <= -0.4:
                return low
            return mid

        mood = label(state['PLE'], 'cool', 'neutral', 'warm')
        energy = label(state['ARO'], 'low', 'moderate', 'high')
        stance = label(state['DOM'], 'following', 'equal', 'leading')

        return f"""[EMOTION STATE]
PLE: {state['PLE']:.2f} | ARO: {state['ARO']:.2f} | DOM: {state['DOM']:.2f}
INT: {state['INT']:.2f} | SEC: {state['SEC']:.2f}
Mood: {mood} | Energy: {energy} | Stance: {stance}
[/EMOTION STATE]"""
```

**说明**：`[EMOTION STATE]` 共三行——两行数值 + 一行定性标签。定性标签由 PLE/ARO/DOM 映射为 Mood/Energy/Stance，帮 LLM 把握整体语气；数值行仍是权威，标签只是有损压缩后的"体感摘要"。

### 3.11 主动行为引擎（`scheduler/proactive.py`）

主动行为规则参见文档 1 第十二章。

```python
class ProactiveEngine:
    """
    职责：周期性审视每个 (character, user) 对，决定是否主动发起对话。
    独立后台心跳，不阻塞主对话管道。
    生成的消息通过 WebSocket 推送给前端。
    """

    def __init__(self, character_manager, memory_manager, llm_client,
                 ws_manager, config: dict):
        self.interval_hours = config["proactive"]["interval_hours"]
        self.ws_manager = ws_manager
        ...

    def tick(self):
        """每次心跳执行一次，遍历所有活跃的 (character, user) 对"""
        for character_id, user_id in self._list_active_pairs():
            if not self._should_evaluate(character_id, user_id):
                continue
            signal = self._evaluate(character_id, user_id)
            if signal.should_act:
                self._generate_and_push(character_id, user_id, signal)

    def _evaluate(self, character_id, user_id) -> ProactiveSignal:
        """
        评估是否应该主动发起对话。参考文档 1 第十二章。
        参考因素：
        - 内部层状态（LON 高、ANT 高）
        - 记忆衰减堆中有即将遗忘的重要记忆
        - 慢心境偏离基线过远
        - 距上次对话时间
        - 连续无回复次数（退缩机制）
        """
        ...

    def _generate_and_push(self, character_id, user_id, signal):
        """生成主动消息，存入记忆，通过 WebSocket 推送"""
        # 1. 用 proactive.txt 提示词生成消息
        message = self._generate_proactive_message(character_id, user_id, signal)

        # 2. 存入 YantrikDB（标记 is_proactive=True）
        self.memory_manager.store_conversation(
            ConversationTurn(
                character_id=character_id,
                user_id=user_id,
                role="assistant",
                text=message,
                is_proactive=True,
                trigger_reason=signal.reason,
                ...
            )
        )

        # 3. 记录到 proactive_log 表
        self._log_proactive(character_id, user_id, signal, message)

        # 4. 通过 WebSocket 推送
        self.ws_manager.push(user_id, {
            "type": "proactive_message",
            "character_id": character_id,
            "message": message,
            "reason": signal.reason,
            "timestamp": now_iso(),
        })
```

**开关与静默时段（v1.1 明确）**：`_should_evaluate` 在评估任何信号之前先做五道硬性拦截，任一命中即跳过该 `(character, user)` 对：

1. 用户级开关 `users.proactive_enabled = 0`
2. 角色级开关 `character_profile.proactive_enabled = false`
3. 当前时刻落在 `quiet_hours`（默认 23:00~08:00，按**用户本地时区**判定）内
4. `proactive_state.silenced_until` 尚未到期（退缩静默期中）
5. `proactive_state.busy_until` 尚未到期（用户近期表示"最近很忙"，检测方式见文档 1 第 12.2 节；用户主动发消息即清空）

`proactive_state` 是退缩状态的唯一权威来源：主动消息发出时写 `last_proactive_at` 并递增 `consecutive_no_reply`；用户回复时把 `consecutive_no_reply` 归零、清空 `silenced_until`。连续 3 次无回复 → 审视间隔翻倍；连续 5 次 → 写 `silenced_until = now + 24h`。规则细节见文档 1 第 12.4 节。

**用户本地时区的来源（v1.3 补充）**：心跳是后台进程，拿不到请求头，所以时区必须落库——存在 `users.timezone`（IANA 时区名，如 `Asia/Shanghai`，见 5.2）。前端每个 API 请求带 `X-Timezone: <IANA 名>` 头（值取 `Intl.DateTimeFormat().resolvedOptions().timeZone`），API 层发现与缓存不一致时更新（内存比对、变化才写库，时机与缓存策略见 6.1）。`_should_evaluate` 判 `quiet_hours` 时读 `users.timezone` 换算；该字段为空（用户从未带过时区头）时缺省按 **`Asia/Shanghai`（UTC+8）**——与前端兜底是同一个值，不是两套兜底（见文档 3 第 9.2 节）。

### 3.12 WebSocket 管理器（`api/routes_ws.py`）

```python
class WebSocketManager:
    """
    职责：管理所有活跃的 WebSocket 连接，按 user_id 分组。
    支持两类推送：
    - state_update：状态变更时推送
    - proactive_message：主动消息推送
    """

    def __init__(self):
        self.connections: dict[str, list[WebSocket]] = {}  # user_id -> connections

    async def connect(self, user_id: str, ws: WebSocket):
        await ws.accept()
        self.connections.setdefault(user_id, []).append(ws)

    def disconnect(self, user_id: str, ws: WebSocket):
        if user_id in self.connections:
            self.connections[user_id].remove(ws)

    def push(self, user_id: str, message: dict):
        """推送消息给指定用户的所有连接"""
        for ws in self.connections.get(user_id, []):
            asyncio.create_task(ws.send_json(message))
```

**WebSocket 端点**：

```
WS /ws/events

连接后，客户端需发送认证消息：
Client → Server: { "type": "auth", "token": "..." }
Server → Client: { "type": "auth_ok" }

之后服务端推送：
Server → Client: { "type": "state_update", "character_id": "...", ... }
Server → Client: { "type": "proactive_message", "character_id": "...", ... }
```

**注意**：一个用户可能同时打开多个角色页面，因此 WebSocket 推送时携带 `character_id`，前端按当前角色过滤。

### 6.1 认证

```

所有后续请求需在 Header 中携带 `Authorization: Bearer <token>`。API 层从 token 中提取 `user_id`，强制注入到所有数据操作中。前端另需携带 `X-Timezone: <IANA 时区名>` 头（用途见 3.11）。**同步时机（v1.4 明确）**：API 层维护 `user_id → timezone` 的进程内缓存（随用户记录首次加载），每个请求只做**内存比对**——一致就零成本；不一致才写一次库并刷新缓存。不要每请求查库比对（白付一次 SELECT），也不要只在登录时同步一次（用户跨时区旅行后要等下次登录才生效）。

**设计说明（v1.1 新增）**：`POST /api/character/create/template` 中，顶层的 `name` 与 `visibility` 是**权威字段**；`overrides` 里的同名键仅作占位，两者不一致时以顶层为准。`overrides` 的用途是承载其余字段的用户改动（含 `theme`、`emotion_overrides`、`locked_fields`）。

`GET /api/character/{id}/versions` 返回 `{ "versions": [ { "version_id": 3, "changed_at": "...", "change_reason": "..." } ] }`。`POST /api/character/import` 接受 `{ "profile": { ... } }`（角色卡 JSON），校验失败时返回 `{ "status": "error", "issues": [...] }` 且不落库。

Body: { "quiet_hours": [22, 7] }            # 示例 2：改静默时段

**主动行为配置说明（v1.1 补齐）**：`GET /api/config/proactive` 返回**全局默认值**，字段与文档 1 第 12.4 节的参数表一一对应——`quiet_hours` 也在其中，设置页的「静默时段」读写就是它，之前这里漏了这个字段，前端展示了却没接口支撑。`PUT` 支持部分更新，只传要改的字段。角色级覆盖（`emotion_overrides.proactive`）不在这里读写，走 `PUT /api/character/{id}`。

**PUT 语义**：`PUT /api/config/llm` 中 `api_key` 为**可选**字段。字段缺省表示"保持原值不变"；传空字符串表示"清除"；传新值表示"替换"。前端在用户没有改动 Key 输入框时**不要发送该字段**，否则会把已存的 Key 清掉。

Server → Client: { "type": "auth_ok" }

状态更新推送：
Server → Client: {
    "type": "state_update",
    "character_id": "char_001",
    "expression": {...},
    "internal": {...},
    "affective": {...},
    "delta": {
        "expression": { "PLE": 0.12, "ARO": -0.03 },

    "type": "proactive_message",
    "character_id": "char_001",
    "message": "在忙吗？突然想起你。",
    "reason": "loneliness_high",
    "timestamp": "..."
}
```


**设计说明（v1.1 明确）**：`state_update` 的载荷是**完整状态**（三层齐全）外加 `delta`，不是增量。前端应整体替换当前状态对象，`delta` 只用于动画触发（判断是否越过呼吸动画阈值）。`state_update` 与 `proactive_message` 都携带 `character_id`：与当前角色匹配才更新面板/聊天区，不匹配时只给该角色打未读红点。

**`delta` 的结构（v1.3 补充）**：`delta` 与 `expression` / `internal` / `affective` **同构**——同样是这三个分组，组内键为维度符号（`PLE`、`ANX`、`AFF`……），值为本次变化量，**可为负**；情感层的单位与状态值一致（0~100）。未变化的维度**可省略也可置 0**，前端不得假设键一定存在，读取一律用可选链兜底（如 `data.delta?.expression?.PLE ?? 0`，文档 3 第 9.6 节即此写法）。呼吸动画判据：`|delta.expression.PLE| > 0.15`（见文档 3 第 7.3、9.6 节）。


## 七、多用户认证与隔离

### 7.1 JWT 认证

```python
# auth/jwt.py
def create_token(user_id: str) -> str:
    payload = {
        "sub": user_id,
        "exp": datetime.utcnow() + timedelta(days=30),
    }
    return jwt.encode(payload, SECRET_KEY, algorithm="HS256")

def verify_token(token: str) -> str:
    payload = jwt.decode(token, SECRET_KEY, algorithms=["HS256"])
    return payload["sub"]
```

### 7.2 隔离层级

| 层级               | 隔离方式                            |
| :----------------- | :---------------------------------- |
| **用户之间**       | JWT 中的 `user_id` 强制注入所有查询 |
| **角色之间**       | `character_id` 强制过滤             |
| **用户与角色之间** | `(character_id, user_id)` 双键      |

### 7.3 角色的归属

- **系统预置角色**：`owner_user_id = null`，`is_public = true`
- **用户创建角色**：`owner_user_id = user_id`，`is_public` 由用户选择
- 无论哪种，`character_user_state` 和 YantrikDB 的记忆都按 `(character_id, user_id)` 隔离

## 十、部署与运行

### 10.1 开发环境

```bash
cd dudulu/backend
uvicorn main:app --reload --port 8000
```

### 10.2 生产环境

```bash
# Web 进程：调度器关掉，否则每个 worker 各跑一份
DUDULU_SCHEDULER_ENABLED=false uvicorn main:app --host 0.0.0.0 --port 8000 --workers 2

# 调度进程：全局只跑这一个
python -m scheduler.run
```

**调度器只能有一份（v1.1 明确）**：APScheduler 随 FastAPI 进程启动，`--workers 2` 会让每个 worker 各起一套调度器，结果是**日沉淀跑两遍、主动消息发两条、`state_changes` 写双份**。所以生产必须：Web 进程里关掉调度器，再单独跑一个调度进程。开发环境 `--reload` 是单进程，不用管。另外沉淀写入本身也要幂等——同一 `(character_id, user_id)` 的同一天只允许一条 `daily_snapshot`，重复触发直接跳过，这样即使调度器意外跑重也不会污染数据。

## 十一、关键设计决策

| 决策               | 选择             | 理由                                       |
| :----------------- | :--------------- | :----------------------------------------- |
| 情感引擎是否用 LLM | 不用             | 确定性、可调试、零成本                     |
| 数值注入方式       | 文本注入         | API 模式下唯一可行，稳定可解释             |
| 记忆检索           | 混合检索         | 情感陪伴需要情感匹配 + 时间近因 + 关系权重 |
| LLM 接入           | 统一接口，双模式 | 模型无关，配置切换                         |
| 流式输出           | SSE              | 单向流，比 WebSocket 简单                  |
| 主动消息推送       | WebSocket        | 与状态更新共用连接，消息类型区分           |
| YantrikDB 部署     | 嵌入式           | 零配置，Python 包直接可用                  |
| 多用户隔离         | JWT + 双键       | 用户之间完全独立，角色之间完全独立         |
| 预览随机           | 不持久化端点     | 向导需要试错，不应污染数据库               |
| 会话管理           | 显式 session_id  | 支持会话沉淀和 turn_count 统计             |
| 主动行为决策       | 确定性引擎       | 避免 LLM 随机性导致行为不稳定              |
| 主动行为频率       | 默认 4.5 小时    | 太频繁打扰，太稀疏失去"主动感"             |
| 连续无回复处理     | 频率降低 50%     | 避免纠缠感                                 |
| 主动消息存储       | 存入 YantrikDB   | 参与沉淀，可被检索                         |
| 删除角色           | 归档             | 支持恢复，记忆不丢失                       |
| 最近消息来源       | messages 表 + YantrikDB 回读 | 索引在 SQLite、正文在记忆库，各司其职      |
| 敏感配置返回       | 掩码 + `has_api_key` 布尔    | 不把 key 下发浏览器，前端也能显示配置状态  |
| 关系阶段返回       | `stage_code` + `stage_label` | 展示文案属前端职责，后端不拼字符串         |
| 角色创建参数       | 顶层 name/visibility 优先    | 避免 overrides 与顶层字段互相覆盖          |
